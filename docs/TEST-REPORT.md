## pi（0.87.0，模型 openai-codex / gpt-5.5，窗口约 272k）

**测试方式**：`scripts/pi-rpc-session.py` 用 pi 的 RPC 模式驱动会话，只加载本扩展（`--no-extensions -e ./adapters/pi/index.ts`），不加载用户装的其他 pi 插件，不保存会话（`--no-session`）。参数用命令行开关调低：允许压缩线 30k，宽限倍数 2，最少腾出空间 10k。

**和 Claude 版的区别**：
- 插件改不了 pi 的原生压缩线。兜底线 = pi 配置的原生压缩点（窗口 − reserveTokens），上限 = 窗口 − pi 默认预留 16384。
- 默认配置下两者相同，插件只在 `agent_settled` 时挑阶段节点主动压缩；用户调大 reserveTokens、让原生压缩提前时，插件在提前的那个点按工作状态取消。

| 51k，没有阶段节点 | 等待 | 通过 |

## Codex 命令行（0.160.1，能力实测）

**测试方式**：`codex exec` / `codex exec resume`，hook 和压缩配置都用 `-c` 临时传入，加 `--dangerously-bypass-hook-trust` 单次跳过 hook 信任确认，不改 `~/.codex/config.toml` 和信任记录。用一个只记日志的测试 hook 观察事件。

| 能力 | 结果 |
|---|---|
| 轮末压缩阈值 `model_post_turn_compact_threshold_percent` | 生效：设 5% 时，一轮结束后自动压缩（72k → 18k），hook 收到 PreCompact / PostCompact（trigger=auto） |
| 一轮中间的压缩后补回笔记 | 通过：把 `model_auto_compact_token_limit` 临时设为 45000，一轮中间压缩后 `SessionStart(source=compact)` 注入的内容在同一轮送到模型 |
| 轮末压缩后补回笔记 | `SessionStart(compact)` 在 `codex exec` 里来不及触发（进程已退出，恢复会话时是 `resume`）。改为压缩后记待补回标记、下一条用户消息时由 `UserPromptSubmit` 注入，通过 |
| 拒绝轮末压缩（PreCompact 返回 `continue:false`，仅在 Stop 之后） | 可行：答复正常给出、不压缩、恢复会话后上下文完整；但该轮记为 `turn_aborted`（interrupted），`codex exec` 退出码为 1 |
| 识别命令结果 | PostToolUse 只有命令和输出文本，没有退出码（`false` 收到空字符串）；退出码在会话记录文件的工具输出里（`"exit_code":1`），需要按会话记录查 |
| 读当前用量 | hook 输入没有 token 数；会话记录里每次请求有 `token_count.last_token_usage.input_tokens`，可作为当前上下文大小 |

### 通过共享后台服务主动压缩（方案 C）

Codex 交互界面默认连到本机共享的后台服务（app-server 守护进程，通信是 Unix 套接字上的 WebSocket + JSON-RPC），没在运行时会自己拉起。插件可以另开一个连接，对会话调用 `thread/compact/start`。测试客户端：`eval/appserver_client.py`（只用 Python 标准库）。

| 场景 | 结果 |
|---|---|
| 用测试客户端模拟"用户会话 + 插件"两个连接 | 通过：插件连接能看到会话并发起压缩，60k → 约 20k；该轮状态 completed，会话继续可用 |
| 命令行 0.160.1 + 后台服务 0.162.1 | 每次打开交互界面都提示"后台服务功能设置不兼容"，要求选择"本次不用后台服务 / 按新设置重启 / 取消"。不用后台服务时插件无法连到会话 |
| 用户把命令行升级到 0.162.1 后 | 不再提示；首次在项目文件夹运行时提示信任文件夹（经用户同意已信任 SmartCompact） |
| 在真实交互界面（tmux 中运行）跑一轮后，从外部对它发起压缩 | 通过：界面显示 "Compacting context… Making room to continue"，结束后显示 "Context compacted · 29s"，没有"已中断"；51k → 约 20k；之后提问能答出压缩前读过的内容 |

**前提和限制**：
- 命令行和后台服务的版本要一致。后台服务会自己更新，命令行是 npm 安装的不会，两边可能再次不一致。
- `codex exec` 不走后台服务；用户选"本次不用后台服务"时也不走。这两种情况插件无法主动压缩，只能退回 Codex 原生行为。
- 一轮进行中的自动压缩仍然无法推迟。

**还没测**：插件在 Stop hook 里判断后，如何在这一轮真正结束后再发起压缩（时机控制）。

## Codex 命令行适配（`adapters/codex`）端到端测试

**环境**：隔离的 Codex 配置目录 `~/.smartcompact-eval/codex-home`（模型设置与用户一致，登录凭据为符号链接），自带独立的后台服务；hook 和信任只写在这个目录里，不碰用户的 `~/.codex`。测试脚本通过后台服务驱动会话（与交互界面同一条路），参数用环境变量调低：允许压缩线 50k，最少腾出空间 10k。

**工作方式**：Stop hook 从会话记录里读出本轮的命令、退出码、改过的文件和上下文大小，按 core 的规则判断；需要压缩时启动后台进程，等会话空闲后发起压缩，发起前再按最近一轮的判断确认一次。压缩后由 SessionStart(compact) 补回笔记，没来得及时在下一条用户消息补回。

| 场景 | 结果 |
|---|---|
| 测试通过后的压缩 | 通过：本轮结束约 1 秒后发起压缩，69k 的会话压缩后继续可用；PostCompact 记为插件压缩 |
| 补回笔记 | 通过：压缩后会话记录里紧接着出现开发者消息形式的进度笔记，包含"tests passed"。模型（GPT-6）不肯原文复述内部上下文，所以用会话记录核对 |
| 决定压缩后，下一轮测试失败 | 通过：后台进程在会话空闲时发现判断已变为"等待"，取消压缩；之后测试通过才压缩 |

**测试中发现并修复**：
- 后台压缩进程用了 Node 只去类型模式不支持的构造函数参数属性写法，一启动就退出、没有日志。已改写，并在 `scripts/check.sh` 里加上 Codex 模块加载检查。
- 决定压缩后若用户马上开始下一轮，压缩会推迟到之后的空闲时刻，期间情况可能变化。已改为发起前再确认。

## Codex 对照评测（18 个连续任务，每组 3 次）

**做法**：在一个已上线的 TypeScript 单仓项目（下称评测项目；题目和隐藏测试涉及它的内部接口，不公开）的三个包上出 18 个连续开发任务，分 3 轮，后面的任务会修改前面任务的结果。一个会话从头做到尾，每个任务要求实现、补测试、跑测试、提交；每轮结束问 6 道记忆题（不许看文件），包括第 1 个任务里随口提到的工单号和客户名。结束后脚本跑 77 项隐藏验收测试（模型看不到）和各包原有测试。出题后先让另一个代理只看题目独立实现，77 项全部通过，确认题目可做。

- 原生组：用户自己的 Codex 设置（gpt-6-astra，xhigh，窗口 87.2 万，80 万自动压缩），不装插件。
- 插件组：同样设置，加 SmartCompact 默认参数（允许压缩线 20 万）。
- 两组各用一个隔离的 Codex 环境，6 个会话同时跑。脚本与题目在 `eval/`，汇总用 `eval/summarize.py long`。

**结果**（成本按 OpenAI 价格比例折算：缓存命中 1、未命中输入 10、输出 80）：

| | 原生组（3 次平均） | 插件组（3 次平均） | 差别 |
|---|---|---|---|
| 总成本 | 4393 万 | 3570 万 | −19% |
| 第 2、3 轮成本（插件起作用的部分） | 3409 万 | 2433 万 | −29% |
| 输入 token | 3164 万 | 2347 万 | −26% |
| 上下文峰值 | 40.3 万 | 20.7 万 | |
| 压缩次数 | 0 | 2（都在刚提交、刚过 20 万时） | |
| 用时 | 80 分钟 | 72 分钟 | |
| 任务完成 / 被催促 | 18/18 / 0 | 18/18 / 0 | 相同 |
| 隐藏验收 | 18/18 任务全部通过 | 18/18 任务全部通过 | 相同 |
| 记忆题 | 54/54 | 54/54 | 相同 |
| 原有测试新增失败 | 0 | 0 | 相同 |

单次成本区间不重叠：原生 3989 万–4938 万，插件 3249 万–3852 万。

**代价与限制**：
- 压缩后模型要多花请求重新熟悉代码：第 2、3 轮插件组平均 134 次请求，原生组 88 次；未命中缓存的输入多约 30%。这些已计入上面的成本。
- 第 1 轮两组都没到 20 万，插件不起作用，插件组反而贵 11%，这是两次运行间的正常波动。
- 成本是按价格比例估算的，Codex 订阅额度的扣法不一定相同。
- 一个代码库、一种任务类型、每组 3 次。

**评测中发现并修复**：`pnpm --filter <包> test` 这类带参数的测试命令原来不被识别为测试；`测试命令 | tail` 的退出码是 `tail` 的，测试失败也会被当成通过。已改为带参数也识别、接管道且未开 pipefail 时不当作结果。

| 用时 | 34.5 分钟 | 37.6 分钟 | |

- 成本几乎全是缓存读取，插件把它降了约 16%；压缩后要重新写缓存、模型也要多花请求重新熟悉代码，抵掉了一部分。Haiku 单次之间请求数差别大（181～269 次），插件组第 3 次比原生组两次都贵，这组数据只能说明有小幅节省。
- 压缩后的记忆题全对，没有忘事。

**评测中发现并修复（提交识别，前后三次）**：
1. Haiku 用 `git commit -q`，没有 `[分支 哈希]` 输出，插件一次都认不出。先改为"命令本身以 `git … commit` 开头、退出码可信且为 0 也算"。
2. 加长后发现 Haiku 常把接管道的测试和提交写在一条命令里，退出码被判为不可信，第 3 次运行 30 次提交一次都没认出，插件等到 26 万才由原生压缩在一题做到一半时触发。试过"退出码只看最后一段"，但 Haiku 提交后常接 `git log`，反而认得更少，撤回。
3. 最后简化为：真的执行了 `git commit`（一段命令以它开头）、工具调用没报错、不是 `--dry-run`，就算一次提交，不再核对输出和退出码。理由是插件只在一轮结束、超过允许压缩线时才压缩，误认一次失败的提交代价很小，而层层核对会漏掉模型的各种写法。用 4 次运行的 121 次真实提交重放，全部认出、没有误认。插件组用这一版重跑了 3 次，压缩全部发生在提交后。

另外，评测脚本最初从流式消息里取输出量，流里的单条消息不带最终输出量，已改为取每轮结束的汇总用量。

**已知设计问题（暂不改）**：Claude 上插件把原生自动压缩挪到约 26 万，和插件"一轮结束时超过宽限线就压缩"的兜底线重合，兜底通常轮不上，而是原生压缩在一轮中间触发。只在过了 20 万后长时间认不出阶段节点时才会发生；提交识别修好后的 3 次重跑里没有出现，先观察。

## Claude 长会话对照评测（60 个连续任务，每组 3 次）

**为什么补测**：30 个任务时原生组只到约 30 万，插件只压缩 1～2 次，省得少、又容易被波动盖住。真实使用中 Claude 原生要接近 100 万才压缩，所以把会话拉长。

**做法**：同一个项目、前 30 个任务不变，再加 5 轮 30 个更大的任务（T31–T60，多数要同时改 2～3 个包，很多会改动前面任务的行为），共 10 轮、60 道记忆题。新任务和隐藏测试由另一个代理出题，并先在一份做完前 30 题的代码上自己实现一遍：T1–T60 的隐藏测试全部通过；反过来在只做完前 30 题的代码上，T31–T60 每题都有测试失败。模型、隔离方式和价格比例与 30 个任务时相同（Haiku 5.5，成本按缓存命中 1、未命中输入 10、写入缓存 20、输出 50 折算）。

| | 原生组 | 插件组 | 差别 |
|---|---|---|---|
| 成本（百万） | 289.1 / 239.3 / 227.9 | 149.6 / 136.2 / 137.9 | 平均 **−44%**，区间不重叠 |
| 输入 token（平均） | 2.05 亿 | 0.85 亿 | −59% |
| 上下文峰值 | 82～96 万 | 21.3～21.8 万 | |
| 压缩 | 0（最高 96 万，还没到原生压缩点） | 7 / 6 / 6 次，全部由插件在 20.2～21.8 万时发起 | |
| 请求数 | 532 / 483 / 446 | 685 / 603 / 631 | +31% |
| 隐藏验收 | 59 / 60 / 60 | 60 / 60 / 60 | 无损失 |
| 记忆题 | 60 / 60 / 60 | 56 / 60 / 58 | 180 道里少答对 6 道 |

- **省在哪里**：原生组越往后每一步都要重读几十万的上下文；插件组每次压缩回到几万，再涨到 20 万左右。压缩后模型要多花约三成请求重新熟悉代码、重新写缓存，这些已计入成本。和 30 个任务（−7%）比，会话越长省得越多。
- **代价：随口提到的细节会丢一些**。插件组少答对的 6 道都是很早之前随口提到、和代码无关的细节（任务 1 的工单号、任务 7 的值班人、任务 31 的客户、任务 34 的机房城市、任务 45 的审计方、任务 46 的提出人）；模型都直接说"不记得"，没有编造。3 次里有 1 次 60 道全对，丢不丢有随机性。代码相关的问题（错误码、配置名、默认值）没有答错。
- **原有测试**：有一个包里 2 个原本就失败的测试，两组都一样；原生组第 1 次模型在 T50 把一个字段改成必填，没同步改用到它的另一个包，导致那个包编译不过、测试没跑起来；另有 1 个原有测试在两组各有失败（原生 1 次、插件 2 次）。
- **用时不可比**：插件组 3 次大部分时间和用户的其他工作（浏览器测试、类型检查等）同时跑，机器负载一度到 44（8 核），所以用时（插件组约 3 小时）反而比原生组长；原生组第 3 次是在空闲时跑的，只用了 100 分钟。成本和 token 不受快慢影响。

**评测中发现并处理的问题**：
1. **插件设置的变量被评测进程继承**：插件通过 `CLAUDE_CODE_AUTO_COMPACT_WINDOW` 调整原生压缩点，从装了插件的会话里启动评测时，原生组也继承了它、在 26 万就压缩。评测脚本改为启动前去掉这个变量，那次结果作废。这也是插件的一个副作用，已写进 README 的常见问题。
2. **压缩结果被当成记忆题的回答**：插件在一轮结束后排队执行 `/compact`，评测脚本只等 15 秒看它是否开始；机器很忙时压缩开始得晚，脚本把压缩的空结果当成了下一条消息的回答，插件组有 3 轮记忆题被记成 0 分。脚本已改为不把压缩的结果（轮数为 0）算作回答；已有结果用 `eval/recall-from-log.py` 从事件日志里按顺序找出每轮的真实回答重新打分（上表即重新打分后的结果；原生组和之前 30 个任务的 9 次重新打分后与原记录一致）。
3. **Node 版本**：App 重启后终端默认的 Node 变成 18，原生组第 3 次第一次运行时，整场测试都跑不起来，作废重跑；评测脚本现在启动时检查 Node 版本。
4. **隐藏验收在空闲时统一重跑**：有 3 题的隐藏测试依赖真实计时，全部跑完后在空闲机器上逐个重跑验收，结果和运行结束时记录的一致。

## Codex App（ChatGPT.app 26.930，自带 Codex 0.160.0）

从安装包 `app.asar` 里的连接逻辑看（未运行 App）：

- 默认：App 自己启动一个 `codex app-server` 子进程，用标准输入输出通信，**不连共享后台服务**。插件无法从外部连到 App 的会话，方案 C 用不上。
- 只有同时满足以下条件时才改连共享后台服务：本机会话、环境变量 `CODEX_APP_SERVER_USE_LOCAL_DAEMON=1`、没有设置 `CODEX_APP_SERVER_FORCE_CLI` / `CODEX_CLI_PATH`、没有自定义 CLI 命令，且 `codex app-server daemon version` 能返回版本。这个开关没有出现在公开文档里。
- **实测（2026-10-14）**：先启动共享后台服务（0.162.1，App 自带的 Codex 查询版本能通过），再带 `CODEX_APP_SERVER_USE_LOCAL_DAEMON=1` 启动 App，App 仍然自己起了 `codex app-server` 子进程。原因：上面的条件还要求"没有配置覆盖"，而 App 主连接本机时总会带上配置覆盖（启用内置的 codex-app-tools 插件等 `-c` 参数），所以这条分支在这个版本里走不到。除非 OpenAI 改了这段逻辑，否则 App 里插件只能补回进度笔记，压缩按 Codex 原生规则。
- **能不能在运行中改原生压缩点（读 Codex 0.160.0 / 0.162.1 源码）**：不能。压缩上限在会话创建时从配置定下，之后每轮用的都是这份快照；运行中重新加载配置只更新 MCP、hook 等少数几项。hook 也不能触发压缩；PreCompact 返回 `continue:false` 能否决，但会中止整轮，下一轮开头又会触发，不可用。
- **可用的兜底**：Codex 自带一轮结束后压缩的设置 `model_post_turn_compact_threshold_percent`（默认关闭）。模型给出最终回复时，上下文超过可用窗口（`model_context_window` × 模型的有效比例，通常 95%）的这个百分比就压缩，不会在一轮中间压缩。它在会话创建时从 `config.toml` 读取，App 和 `codex exec` 都会生效。按宽限线约 26 万算：窗口 87.2 万时约为 31。终端交互界面里插件通常先在阶段节点压缩；Codex 自己压缩后 PostCompact hook 会撤销插件排队中的请求，不会压缩两次（读代码得出，未实测）。没有做成默认安装，也没有实测效果。
- App 和命令行共用 `~/.codex`，所以 hook（压缩后补回笔记、识别信号）在 App 里同样会运行，但需要在 App 里信任一次。
